## 1. Runtime-realizable expertise budgets

`validate_evaluation_budget_reachability()` now validates every selected evaluation profile before production runner execution. It uses the actual `FrozenRootAgent` control flow:

```text
maximum generation turns = max_tool_calls + 1 final-answer turn
maximum reachable generated tokens = maximum generation turns × max_new_tokens_per_turn
valid profile iff declared max_output_tokens <= maximum reachable generated tokens
```

The generated-token budget remains a hard cumulative runtime cap in `FrozenRootAgent.run()`. Each turn receives `min(max_new_tokens_per_turn, remaining cumulative budget)`, and the recorded `model_output_tokens` is the actual number of generated tokens. Tool/agent iterations are governed independently by `max_tool_calls` and `exact_tool_calls`. Early stopping can consume less than the cap; it does not change the expertise x coordinate.

The production per-turn limit is now 1,000 tokens. The resulting reachability audit is:

| Profile | Tool calls | Maximum generation turns | Declared cap | Maximum reachable |
|---|---:|---:|---:|---:|
| `direct` | 0 | 1 | 1,000 | 1,000 |
| `max5` | ≤5 | 6 | 3,000 | 6,000 |
| `max20` | ≤20 | 21 | 6,000 | 21,000 |
| `exact20` | exactly 20/no early return | 21 | 10,000 | 21,000 |

The exact-20 behavior was not weakened: early final answers are converted into explicit continuation turns until the exact tool-call requirement is met, subject to the independent cumulative token cap. A real-loop regression fixture performs five typed tool actions plus a final generation and consumes exactly a declared 3,000-token cap. A deliberately impossible 3,000-token profile with five tool calls and 128 tokens per turn fails early because its maximum is 768.

Expertise semantics are unchanged: one point is emitted per `condition × budget`; x is configured generated-token cap per example, and y is the benchmark aggregate strict/lenient score. Individual examples are never curve points. The 3,000-token anchor remains unchanged.

## 2. Production study-bank snapshot enforcement

Study record-bank sidecars now declare one of:

- `production_frozen_base` — generated by the actual frozen candidate model without shuffled correspondence;
- `synthetic_deterministic_smoke` — deterministic development-only records;
- `synthetic_shuffled_correspondence_control` — non-production control records.

Production `train-latent` and `peek-study` now resolve/fingerprint the actual model and tokenizer snapshot before loading records. They call the common record loader with both hashes as required expectations and `require_production=True`. Loading fails closed when the bank mode is not `production_frozen_base`, either stored hash is absent/null, the consumer omitted either expected hash, or either actual hash differs. Matching only canonical model ID/revision is insufficient.

The check occurs before model instantiation and before latent/PEEK optimization. Worker shard merging also requires identical bank modes and snapshot identities. Dependency provenance identity now incorporates `study_bank_mode`, so a downstream parent descriptor changes if a bank is relabeled. Production memory/evaluation dependency chains can therefore originate only from the production gates; synthetic banks remain available to `smoke-eval` and other explicitly non-production readers, which still validate provenance and content integrity.

The equivalent-consumer audit found two other record readers: `replay-report` is a study-bank diagnostic that does not load/consume a model snapshot, and `smoke-eval` is explicitly a development smoke path. Neither is a production model-dependent consumer, so both retain non-production access. Candidate generation itself writes the mode and exact snapshot pair. The legacy `round2_peek_smoke.py` remains a clearly named development script and does not create an eligible production baseline.
